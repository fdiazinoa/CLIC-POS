# Caja6 nonrotating session AUTH and remaining binding-proof gap

The existing published ERP c348 `/api/sync/auth` renews a sync session after validating the registered device binding. Its public response contains AUTHORIZED/success, token/syncToken aliases, tokenExpiresAt and tenant/terminal/device aliases. It does not rotate the binding token. It supplies neither company/store re-attestation nor independently scoped binding-lifetime evidence. `/terminals/register` can rotate a binding token and is never called by the new entry point.

`apiSyncAdapter.renewCaja6BoundSessionOnly()` is an explicit public canonical adapter operation, not an automatic scheduler action or UI/global hook. It delegates to a small scoped transport using the existing origin, tenant, company, store, terminal and literal device SHA256 of the previously reviewed Clic-Suite/Caja6 policy. It requires the existing ERP_REGISTER binding/token and canonical credentials. It makes exactly one POST to `/api/sync/auth`, with no redirects, fallback or register recovery. The entire exchange is serialized and pins credentials/config/binding through response and persistence. Other POS flows are unchanged.

Only session token/expiry/update time and an additive `LOCAL_OBSERVATION_OF_ERP_SYNC_AUTH` record are saved. That record contains the observed route/origin/tenant/terminal/device and local observation time. It is a local record of AUTH, not ERP-issued binding proof, company/store re-attestation, signature, fiscal permission or evidence of provider acceptance. Device token, source, old expiry/update dates, unknown metadata, pairing, configuration and financial state are preserved literally. A generic session expiry is never copied into deviceTokenExpiresAt.

The new strict CAS writer uses the existing canonical credential queue and native Preferences writer, awaiting native persistence without swallowing failure. It verifies captured raw canonical bytes/generation and context before/after the native await, then writes only canonical/session legacy mirrors. Preferences and localStorage are separate stores: this does not claim atomic cross-store commit. A native failure, local storage failure, or concurrent drift returns HOLD; a partial native write after a concurrent change is not successful renewal and must not be advertised as durable Android validation. Later queued canonical writers remain serialized. Existing permissive generic save APIs remain unchanged.

## Deliberately unresolved fiscal HOLD

FiscalBoundContext remains byte-identical and still rejects expired deviceTokenExpiresAt and non-ERP_REGISTER sources. The observed historical device date may have been copied from a 24-hour session expiry by older setup flows. Its provenance is ambiguous. Renewing a session cannot legitimately erase, null, relabel or supersede that historical binding date. An expired date therefore remains `FISCAL_TERMINAL_AUTH_REQUIRED` after successful AUTH. This change does not unlock readiness, receipt preparation, ISSUE or formats.

The installed APK1.1.531 cannot exercise new source code without a future separately authorized APK. No build/install/device/ERP request, sale/NCF, receipt, claim, issue, migration, flag, grant or credential operation is performed by this code preparation task. A future normal AUTH would change ERP session/last_seen/audit under its existing semantics; it must not be described as read-only or as validation of the new native code.

## Proposed ERP extension — NOT implemented or currently accepted

A jointly reviewed successful AUTH response could expose a versioned bindingEvidence DTO only after current binding/device/company/store authorization and CAS. Proposed fields would include exact scope and origin, explicit binding-token fingerprint/algorithm, lifetime basis (`REVOCABLE_NO_INDEPENDENT_EXPIRY` or a real independent expiry), observation time and a documented link to the returned session. These are design proposals, not an existing endpoint/schema or wire facts. POS currently accepts no such evidence and cannot construct it locally to bypass its fiscal guard. A real independent expiry or revocation must never be overwritten.

Directed synthetic tests use real loopback HTTP and SQLite-backed canonical/local/native storage ports, with restart-style rereads, malformed/ambiguous replies, redirects/timeouts, scope/config/credential drift, native failures and concurrency. These demonstrate host transport/storage behavior only, not real ERP or Android Preferences integration. Existing fresh-credential receipt/status/selection, default ISSUE HOLD and No fiscal/Legacy tests remain required regressions.
