# POS optional binding AUTH evidence V1

Reference: ERP `a73cd49fa47e2e0d645c3cdf20bcdd5975864edf`, `docs/pos-binding-auth-evidence-v1.md`. ERP defines an optional dormant opt-in field on its existing `POST /api/sync/auth`; this POS change does not enable its server flag, enroll a terminal, deploy/apply SQL or establish readiness. Historical device expiry/provenance reconciliation remains explicitly unresolved. `FiscalBoundContext.ts` is unchanged.

## Consumer

Normal AUTH handles present `bindingEvidence` before legacy identity/bootstrap/device/session persistence; invalid/null/unknown proof is HOLD, never legacy fallback. The existing explicit Caja6-only renewal uses this same validator and store. Without evidence and without a prior native envelope, existing legacy persistence remains. With a prior envelope, proofless AUTH saves a new session with current evidence null and retains all historical evidence. Other operational flows and Pancuvi configuration are untouched.

The exact V1 root/nested keys, schema/source/decision, canonical HTTPS origin and full tenant/company/store/terminal/device scope must match captured authorized context. Both fingerprints are lowercase SHA256 of literal UTF8 string bytes, without coercion, trim, Unicode normalization, decoding or JSON hashing. ISO dates must retain UTC millisecond form; session expiry equals the same AUTH response tokenExpiresAt, remains future when newly consumed, and is24hours after ERP observedAt. No local observation-clock/skew tolerance is invented. Stored historical integrity can be checked after its session expires; an expired association is never returned as current usable proof. Subsequent ERP evidence must have a newer observedAt than retained evidence, preventing cached/out-of-order responses from replacing the current association.

Caja6 normal AUTH uses one bounded direct request with six current headers, no redirects/retry/register/fallback; normal legacy paths outside this scope retain their existing transport. Explicit Caja6 AUTH retains its original scope/device checks. New evidence neither relabels deviceTokenSource nor removes/replaces deviceTokenExpiresAt. Fingerprint matching is an ERP observation, not a signature, offline authorization, fiscal permission or acceptance DGII.

## Durable association and restart

Native SQLite adds private `terminal_auth_evidence_current` and append-only `terminal_auth_evidence_history`, with typed access only. They are not generic documents, sync/recovery collections or Outbox payloads and are not returned by collection exports. They contain private credential state; an authorized full application/database backup remains sensitive and is not claimed to exclude these tables. No raw credentials/evidence are logged or transported by the store.

One native transaction validates full raw prior-envelope CAS/revision, preserves the complete captured binding metadata and commits the new session/evidence-or-null plus immutable history. SQL COMMIT is the association authority. A lost COMMIT ACK yields HOLD/readback; no deletion, compensating rollback, second AUTH or issue occurs. Failure before commit rolls back both writes.

Preferences/localStorage are compatibility projections after SQL commit, never the association authority. Native persistence exceptions, quota failures or drift yield HOLD. Each projection and rehydration rechecks the current SQL revision and canonical before/after bytes. Recovery may publish only the known before/after canonical snapshots, with matching existing native projection and unchanged binding mirrors; unrelated changes are HOLD. A failed projection is not a successful or partially accepted association. The async getter compares the currently authorized bound origin/full scope/session, pins config/profile during the read, rechecks SQL revision after projection awaits, and verifies the whole envelope and all effective canonical/native/session/binding mirrors; it never pairs an old effective session with new proof. Once projection starts, its marker keeps synchronous readers failclosed on cold startup until the native envelope is rehydrated, preserving raw snapshots instead of migrating/merging them prematurely. There is a SQL-COMMIT-to-first-marker crash window: an early legacy synchronous reader can still observe its old session before async recovery. This is not claimed as a global boot fence or cross-store atomicity. The asynchronous paired-proof getter rejects that incomplete projection; it cannot expose the new proof with the old session, and the fiscal guard remains unchanged/closed. Sync credential readers never receive evidence; after verified publication they read the coherent canonical projection rather than merging stale legacy session keys.

Async canonical credential reads and normal AUTH recover before treating a durable session as usable; the explicit renewal also recovers first. Expired historical envelopes may rehydrate so normal AUTH can renew, preserving history. Generic credential changes cause an association mismatch/HOLD instead of attaching old evidence to a new token/binding. A proofless renewal clears only current association, not history. There is no TTL/reset/rebind or fiscal date repair.

## Stop and evidence limits

New optional-proof persistence requires native typed SQLite capability; unsupported adapters HOLD if proof is present. No-proof/no-envelope installations preserve legacy behavior. Receipt/claim/default ISSUE, formats and e-factura activation remain closed. E34 negative and history-only post-Z are unchanged. No sale, NCF reservation, provider submission or claim is created here.

Tests use synthetic AUTH vectors, real host SQLite via the existing native adapter bridge and real loopback HTTP. They cover literal hashing, exact DTO, scope/aliases/date mismatches, rollback at history/current write, lost COMMIT ACK, each projection failure and restart, stale responses/config/credential drift, proofless renewal, expired-journal renewal, immutable history, and both actual normal adapter persistence and explicit Caja6 composition. This is not proof of deployed ERP policy, real Android Preferences durability or distributed server cache coherence. Those require their own authorized environment/device gates; no new server flag or enrollment is implied by a candidate APK.
