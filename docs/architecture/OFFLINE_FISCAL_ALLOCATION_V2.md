# Finite fiscal allocation authority

V2 is additive and initially disabled by the ERP. It authorizes the finite NCF allocations already owned by one Master/device. It has no separate day deadline, permit pages or sale quota. Actual fiscal range expiry, ownership, issuer/environment, explicit revocation and clock integrity remain checks for new payments. V1 permits and their historical expiry/recovery semantics are unchanged.

Background `prepareOfflineAuthority` requests one compact authenticated allocation authority. If V2 is unavailable it retains V1 preparation. A valid V2 avoids downloading a new V1 1024-permit pool. Checkout makes no HTTP request. The payment modal displays remaining NCF by type for V2, instead of calling these numbers workflow permits.

Native PREPARED stores the candidate number, checkout/transaction IDs, exact cart/table context and immutable issuance snapshot, with a durable pending number owner. It does not issue a receipt or advance any number. SQLite receipt/buffer/authority guards fence other writers of that pending number. A guarded zero-effect edit tombstones the attempt and releases the candidate; EFFECT_POSSIBLE retains its identity permanently. At financial commit the existing native writer checks authority and exact persisted snapshots, then atomically advances fiscal/internal/global numbers, consumes the pending claim, inserts the issued NCF receipt, and writes sale/history, table settlement, financial effects and the existing Outbox birth. No second queue is introduced.

A schema 3 `OFFLINE_FISCAL_ALLOCATION_V2` birth identifies the downloaded authority and local checkout, not a fabricated V1 permit. ERP intake verifies the immutable downloaded authority, scope and finite membership and enrolls that same transaction/NCF. Unique issuer/environment/NCF, allocation/sequence, checkout/transaction and table account prevent a second effect. A timely historical birth can reconnect after genuine range expiry. Withdrawn authority retains the paid birth HELD for review; it never instructs another cash collection. Provider dispatch keeps the existing permanent fence and ambiguous outcomes remain GET-only.

Deployment depends on the ERP additive migration/readers first, with issuance OFF. Configure `POS_FISCAL_OFFLINE_ALLOCATION_V2_ENABLED=true` only with exact comma-separated company and ERP terminal allowlists in `POS_FISCAL_OFFLINE_ALLOCATION_COMPANY_IDS` and `POS_FISCAL_OFFLINE_ALLOCATION_TERMINAL_IDS` after independent code/native/PG integration gates. Do not use local terminal labels as ERP UUIDs. Keep all existing V1 readers and modern rotated credentials. This document does not authorize deployment or a real operational charge.

Rollback disables new V2 preparation/selection for the connected cohort; a device already offline cannot observe remote withdrawal until reconnect. Retain all V2 schema/intake/recovery/dispatch readers and completed receipts. Do not decrement numbers, remove pending paid claims, clear the Outbox, rewrite old permits or downgrade/reset a device. Explicit withdrawal and operational claim reconciliation must preserve possible/committed payments.

Developer tests: `tests/offlineFiscalAllocation.test.ts` exercises real Node SQLite through the native adapter, including day 1/8/30, finite exhaustion, table CASH + 10%, guarded edits, competing writers, true fiscal expiry, rollback and COMMIT acknowledgment loss. Actual Android checkout and independent QA/sync/performance are separate required gates. ERP tests have portable embedded PostgreSQL CI coverage and an explicit localhost-only PostgreSQL 17 profile; neither is a production migration.
