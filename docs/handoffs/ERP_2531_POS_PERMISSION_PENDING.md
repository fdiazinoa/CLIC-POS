# Pendientes POS del PR ERP #2531

Handoff contractual: [ERP #2531](https://github.com/fdiazinoa/CLIC-ERP/blob/d9df7c69151cfe9cead30a97f2b09c7d819bc7fc/docs/development/pos-permission-parity-handoff.md). Cambios limitados al consumidor POS; sin modificar ERP ni generar APK.

## Cambios concretos

- `CASH_IN_OUT` pertenece ahora a la unión `Permission`; se elimina el cast del guard existente en POSInterface. No cambia la autorización de movimientos.
- El catálogo del editor local incluye los cinco `POS_CATALOG_CONFLICT_*` ya utilizados en runtime. No se añaden a roles ni defaults. El editor ERP-managed continúa bloqueado, y ADMIN/ALL conservan sus protecciones existentes.
- `normalizeErpRole` conserva `zReportConfig` y el alias contractual `z_report_config`. Sólo admite FINANCIAL, PAYMENTS, CASH_DETAILS, KPIS y AUDIT, sin claves adicionales; deduplica el array (máximo cinco entradas como el contrato ERP). Configuración malformada o aliases contradictorios rechazan el snapshot completo antes de persistirlo. Los aliases iguales pueden tener distinto orden.
- Registros antiguos sin configuración o con ambos aliases nullish continúan siendo válidos. Un snapshot completo no mezcla restricciones previas; `{hiddenModules: []}` limpia explícitamente. La ausencia del catálogo (`roleRows: null`) conserva el snapshot offline. No se completan permisos con defaults, ni se expanden ALL o permisos personalizados; se conserva maxDiscountPercent.

## Devoluciones: decisión funcional pendiente

La ruta activa `POSInterface` → `useSupervisorAuth` → `SupervisorModal` solicita `CAN_REFUND`; los checks de usuario y supervisor comparan la clave literal o ALL. La política PIN `terminalAuthorizationPolicy` reconoce CAN_REFUND. `SupervisorAuthModal` es un componente separado y no es la ruta usada aquí. ERP publica POS_RETURNS.

No se modificó ese contrato: un rol legacy con sólo CAN_REFUND y un rol al que se retiró POS_RETURNS pero conserva CAN_REFUND son indistinguibles con el array plano actual. Un fallback OR podría reautorizar una revocación; cambiar sólo la solicitud rompería legacy. **Pendiente acordar un marcador/migración autoritativa que distinga legacy de revocación canónica** antes de unificar el guard, la aprobación del supervisor y la política PIN bajo POS_RETURNS. No se creó otro permiso ni se concedió acceso automáticamente.

No se añadieron secciones ni se alteró impresión inicial de venta. Estos módulos no implican ocultar automáticamente otras secciones, anexos o pantallas que nunca dependieron de ellos.

Pruebas locales focales: normalización camel/snake, legacy, config inválida, aliases contradictorios, limpieza explícita, snapshot completo y persistencia/reapertura con el adaptador IndexedDB y fake-indexeddb; revocación y conservación de permisos personalizados/ALL/maxDiscountPercent; catálogo de conflictos sin defaults nuevos y checks existentes de concesión/denegación.
