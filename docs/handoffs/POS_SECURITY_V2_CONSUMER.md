# Consumidor POS de seguridad v2 (sin activación operativa)

Referencia fija: [ERP 8e2b335, contrato PR2533](https://github.com/fdiazinoa/CLIC-ERP/blob/8e2b3353504b964d50f5706a2bed1c983e2aae91/docs/development/pos-return-permission-contract-v2.md). PR POS1011 incorporado sin cambiar sus reglas de editor/configuración. El contrato ERP está definido; sus helpers preparados no son handlers ni acuerdos operativos.

- `PosSecurityV2Contract` valida el envelope/ref/control públicos y el SHA256 canónico con el digest normativo. Los permisos wire son exactos; `permission_keys` es espejo obligatorio. La validación precede a la proyección por el normalizador ERP existente en modo v2, sin heredar PIN ni completar permisos.
- `PosSecurityV2Consumer` requiere transporte y binding autenticados inyectados. No tiene implementación HTTP ni instancia conectada, endpoint de activación o generador de aprobaciones. `announce/accept` publican únicamente los campos normativos; ACCEPTED conserva CURRENT_UNCHANGED. ACTIVE sólo puede recibirse por el puerto confiable futuro (fixtures en pruebas).
- La seguridad se guarda en `syncMetadata`, un checkpoint por tenant-terminal, con floor, control, referencias por binding/acuerdo/digest y referencia aplicada. Roles, usuarios y checkpoint se publican en la misma transacción existente `saveDocumentsAtomically`, con CAS durable. Las listas vacías reemplazan. Duplicados exactos no escriben; revisión antigua/conflictiva, hash/binding/acuerdo incorrectos y estado corrupto fallan sin publicación parcial.
- Las entradas preparadas `receiveConfig`, `receiveConfigPush` y `receiveManifest` extraen los carriers normativos. Referencia vigente y partición se validan antes de descargar; no hay caché permisiva ni 304 sin checkpoint aplicado. No se modifica el transporte de catálogo ajeno a seguridad.
- El boundary de almacenamiento existente impide escrituras legacy de roles/usuarios tras floor2. Las sustituciones de metadata conservan los checkpoints dentro de la transacción; los resets no reducen el floor. La lectura durable de checkpoints es estricta y no usa fallback de localStorage ni decoder SQLite tolerante.
- El guard de devolución, el modal y la revalidación de supervisor usan el mismo resolver: CURRENT conserva CAN_REFUND anterior; v2 exige POS_RETURNS o ALL literal y membresía vigente. La política PIN sigue siendo exigencia adicional. Cancelación/contexto cambiado/revocación durante autorización no concede acceso.
- El contexto autenticado de autorización se proveerá mediante `configureReturnSecurityContext`. Por defecto está desconectado. Un floor2 guardado sin ese contexto, suspendido o con otro acuerdo/binding no reutiliza roles antiguos; falla cerrado para devoluciones. No se infiere activación del marcador del rol, versión APK o transporte V3. Ninguna ruta del producto llama a negociación real en esta tarea.

## Pendientes de integración ERP

Faltan los handlers `/security-contract`, persistencia ERP autorizada de bindingEpoch/floor/acuerdos/revisiones, evidencia de aceptación/rollout y wiring de endpoints/snapshots/manifest/CONFIG_PUSH. La integración futura debe inyectar el transporte autenticado y el contexto real; no tomar identidades de payload libre ni activar desde el POS. No hay migración CAN-only ambigua. Un binario antiguo que no conoce el floor sigue sin ser un downgrade acreditado como seguro.

## Evidencia y límites

Las pruebas locales usan transporte simulado y estados ACTIVE exclusivamente de fixture, IndexedDBAdapter con fake-indexeddb, hash vector fijado en el handoff, reemplazo/revocación, reapertura, CAS concurrente y preservación de metadata. El enlace hook/modal/App y SQLite se revisa estáticamente; los helpers de autorización se prueban localmente. No se prueba UI completa, negociación ERP real, Android SQLite ni dispositivo MYKON. Sin APK, instalación, despliegue, benchmark o certificación. Build y checks obligatorios se reportan por QA independiente.
